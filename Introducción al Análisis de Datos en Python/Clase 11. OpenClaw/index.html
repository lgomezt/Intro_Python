Sección 01 · Conceptos

Introducción

Qué es OpenClaw, por qué corre en local y qué cuidados de seguridad implica eso.

¿Qué es OpenClaw?

OpenClaw es un asistente personal de IA, de código abierto, que se ejecuta en tu propia computadora. Su sitio oficial lo describe como The AI that actually does things: lee correos, agenda eventos, hace check-in en vuelos y conversa con vos a través de aplicaciones de mensajería como WhatsApp, Telegram o Discord.

A diferencia de un chatbot web, OpenClaw vive como un proceso (gateway) en tu PC. Recibe mensajes desde tus apps de chat, los procesa con un modelo de lenguaje (que vos elegís) y ejecuta acciones en herramientas reales.

¿Por qué es útil para esta clase?

  • Es un caso real de integración entre datos, APIs y modelos LLM.
  • Permite ver de cerca cómo se diseña un agente que hace cosas, no solo responde.
  • Lo configuramos en local, así que no pagamos hosting y mantenemos el control.

Concepto clave: «local» y seguridad

Cuando decimos deploy local queremos decir que el servicio corre dentro de tu computadora: tu máquina es el servidor. Los archivos de configuración, las claves y el historial viven en una carpeta tuya (~/.openclaw/). Si apagás la PC, el asistente se apaga.

Lo que dice la documentación oficial OpenClaw no está diseñado como una frontera de seguridad multi-tenant para múltiples usuarios adversarios. Asume un operador confiable por gateway: vos. El gateway por defecto escucha solo en loopback (no expuesto a internet) y exige autenticación.

Implicancias prácticas para vos

  • Las claves de API que cargues quedan en tu disco. Tratá la PC con la misma seriedad que tratarías un .env de producción.
  • Permisos sugeridos: directorios 700, archivos 600.
  • Si alguna vez exponés el gateway fuera de tu máquina, agregá autenticación por token y firewall.
  • Usá openclaw doctor y la opción de auditoría de seguridad antes de conectar canales sensibles.
Sección 02 · Empezando

Pre-requisitos

Lo que tu computadora necesita tener antes de instalar OpenClaw: Node.js correcto para tu chip o arquitectura.

Antes de empezar

Lo único obligatorio según la documentación oficial:

  • Node.js 24 recomendado, o como mínimo Node 22.16+.
  • Sistema operativo: macOS, Linux o Windows (nativo o WSL2).
  • En macOS, la app de escritorio (opcional) requiere macOS 15+.

Elegí tu sistema operativo. Toda la guía se adapta a tu elección:

Instalar Node.js

¿Qué es Node? Pensalo como el «intérprete de Python» pero para JavaScript. Cuando vos escribís un script .py, lo corrés con python script.py: Python es el motor que ejecuta el código. Node.js cumple exactamente el mismo rol con archivos .js: es lo que permite que un programa escrito en JavaScript se ejecute en tu computadora, fuera de un navegador.

¿Por qué lo necesitamos? OpenClaw está escrito en JavaScript/TypeScript y se distribuye como un paquete de npm (el equivalente de pip en Python). Sin Node, tu computadora no sabe cómo ejecutar OpenClaw, igual que sin Python no podrías correr pandas.

Lo descargamos del sitio oficial: nodejs.org/en/download. Nunca instales Node desde sitios no oficiales — es un programa que va a poder ejecutar código en tu PC, así que la fuente importa.

Equivalencias rápidas con Python
  • python ⇄ node (el motor)
  • pip install paquete ⇄ npm install paquete
  • requirements.txt ⇄ package.json
  • venv ⇄ no aplica directo: cada proyecto tiene su node_modules/

Antes de descargar: ¿qué chip tiene tu Mac?

Hay dos familias de Macs y se descarga un instalador distinto para cada una:

  • Apple Silicon — chips M1, M2, M3, M4. Todos los Macs nuevos desde fines de 2020.
  • Intel — Macs anteriores a 2020 (y algunos modelos vendidos hasta 2022).

Para saber cuál tenés, hacé cualquiera de estas dos cosas:

  1. Por interfaz: menú Apple (arriba a la izquierda) → «Acerca de este Mac». Vas a ver una de estas dos líneas:
    • Chip: Apple M1 / M2 / M3 / M4 → es Apple Silicon.
    • Procesador: Intel Core ... → es Intel.
  2. Por terminal: abrí la Terminal y ejecutá: 
    uname -m
    Si responde arm64 → Apple Silicon. Si responde x86_64 → Intel.

Descargar e instalar

  1. Entrá a nodejs.org/en/download.
  2. Elegí versión LTS (la que dice 24.x), formato macOS Installer (.pkg), y la arquitectura correcta:
    • Apple Silicon → ARM64
    • Intel → x64
  3. Abrí el .pkg y seguí los pasos del instalador.

Cuando termine, abrí la Terminal y verificá:

node --version
npm --version

Tienen que devolver dos números de versión (algo como v24.x.x y 10.x.x). Si dice command not found, cerrá y volvé a abrir la Terminal.

Antes de descargar: ¿qué arquitectura tiene tu PC?

Casi todas las PCs Windows son x64 (Intel o AMD), pero los modelos modernos tipo Surface Pro X / Surface Pro 9 con chip ARM, y algunos laptops nuevos con Snapdragon, son ARM64. Necesitás el instalador correcto.

Para saberlo:

  1. Por interfaz: presioná Win + I → Sistema → Información. Buscá la línea «Tipo de sistema»:
    • PC basado en x64 → es x64 (lo más común).
    • PC basado en ARM → es ARM64.
  2. Por PowerShell: 
    echo $env:PROCESSOR_ARCHITECTURE
    Si responde AMD64 → x64. Si responde ARM64 → ARM.

Descargar e instalar

  1. Entrá a nodejs.org/en/download.
  2. Elegí versión LTS, formato Windows Installer (.msi), arquitectura x64 o ARM64 según lo que averiguaste.
  3. Abrí el .msi y aceptá los valores por defecto. Asegurate de dejar marcada la opción «Add to PATH».

Abrí PowerShell y verificá:

node --version
npm --version

Tienen que devolver dos números de versión. Si PowerShell dice que el comando no existe, cerrá y volvé a abrir la ventana: el PATH se actualiza solo después de reabrirla.

¿Ya tenés Node, pero quizá viejo?

Verificá que sea 22.16 o superior:

node --version

Si te aparece algo menor (por ejemplo v18.x o v20.x), descargá el LTS desde nodejs.org/en/download e instalalo encima: el instalador se encarga de actualizar.

Sección 03 · Manos a la obra

Instalación

Seis pasos numerados para llegar de cero a un agente que te responde por WhatsApp con Gmail y Calendar conectados.

1

Verificar si OpenClaw ya está instalado

Antes de instalar nada, comprobemos el estado actual de tu PC.

Abrí la Terminal (Cmd + Espacio → escribí Terminal) y pegá:

openclaw --version

Si responde con un número de versión, ya tenés OpenClaw instalado. Si responde command not found, no está instalado y podés saltar al paso 2.

Abrí PowerShell (tecla Windows → escribí PowerShell) y pegá:

openclaw --version

Si te aparece CommandNotFoundException o no se reconoce como un comando, no está instalado: avanzá al paso 2.

Si dice que sí está instalado: ¿reinstalar desde cero?

Si querés empezar limpio (recomendado para esta clase, así todos partimos del mismo estado), usá el desinstalador oficial: 

openclaw uninstall

Versión no interactiva (responde sí a todo):

openclaw uninstall --all --yes --non-interactive

Si el comando ni siquiera existe pero sospechás que quedaron restos

Eliminar el demonio (gateway) y archivos de estado:

launchctl bootout gui/$UID/ai.openclaw.gateway
rm -f ~/Library/LaunchAgents/ai.openclaw.gateway.plist
rm -rf "${OPENCLAW_STATE_DIR:-$HOME/.openclaw}"
rm -rf /Applications/OpenClaw.app
npm rm -g openclaw 2>/dev/null || true

En PowerShell, eliminar tarea programada y archivos de estado:

schtasks /Delete /F /TN "OpenClaw Gateway"
Remove-Item -Force "$env:USERPROFILE\.openclaw\gateway.cmd"
Remove-Item -Recurse -Force "$env:USERPROFILE\.openclaw"
npm rm -g openclaw
2

Crear cuenta en OpenRouter y conseguir API key

Hacemos esto antes de instalar OpenClaw porque el instalador es interactivo y te va a pedir la key durante la configuración. Tenerla copiada en el portapapeles te ahorra tener que abandonar el wizard a mitad de camino.

Para esta clase usamos OpenRouter como proveedor de modelos: un único punto de acceso a decenas de LLMs (DeepSeek, Google, OpenAI, Anthropic, etc.). Pagás solo por lo que consumís.

  1. Entrá a openrouter.ai y creá una cuenta (Google o GitHub funcionan bien).
  2. En el menú de tu usuario buscá Credits y cargá USD 5. Va a alcanzar de sobra para la clase.
  3. Andá a Keys y creá una API key nueva. Copiala ahora: empieza con sk-or-....
Cuidado con la clave Tratá esa key como tu contraseña. No la pegues en chats, ni en repos públicos, ni en capturas que vayas a compartir.
3

Ejecutar el instalador y pasar por el wizard

El instalador hace tres cosas seguidas, sin que vos tengas que pensar en cada una:

  1. Detecta tu sistema operativo e instala Node si falta.
  2. Instala el paquete openclaw vía npm.
  3. Arranca un wizard interactivo que configura todo el resto.

El comando para arrancar

En la Terminal:

curl -fsSL https://openclaw.ai/install.sh | bash
Si falla con «EACCES» o «permission denied» Quiere decir que tu Node está instalado en una ruta de sistema (típico del instalador oficial .pkg desde nodejs.org, que deja el directorio global de npm en /usr/local/lib/node_modules, propiedad de root). En ese caso, instalá el paquete con sudo: 
sudo npm install -g openclaw@latest
Si instalaste Node con Homebrew, nvm, fnm o volta, el prefix vive en tu home y no hace falta sudo. Para chequear cuál es tu caso: 
npm config get prefix
Si devuelve algo bajo /usr/local → necesitás sudo. Si devuelve algo bajo /opt/homebrew, ~/.nvm o similar → no.

Efecto colateral del sudo: si instalaste o arrancaste OpenClaw como root, la carpeta ~/.openclaw queda con dueño root y después no vas a poder guardar API keys (ni ningún cambio de configuración) desde tu usuario normal. El error típico es permission denied al setear keys. Devolvé el dueño a tu usuario con: 

sudo chown -R $(whoami) ~/.openclaw

$(whoami) se reemplaza solo por tu nombre de usuario. El -R aplica el cambio a todo lo que hay adentro (workspace, credenciales, logs).

Antes de empezar: por defecto, PowerShell bloquea la ejecución de scripts. Habilitá la política RemoteSigned solo para tu usuario (no requiere admin) corriendo esto una vez: 

Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

Si te pregunta confirmación, respondé S (Sí) o Y. Sin esto, el instalador falla con un error de execution of scripts is disabled.

Después, en PowerShell:

iwr -useb https://openclaw.ai/install.ps1 | iex
Importante en Windows Si vas a conectar WhatsApp (lo vas a hacer en este mismo paso), asegurate antes de tener Git en el PATH: 
winget install --id Git.Git -e

El wizard, prompt por prompt

Cuando arranque el wizard vas a ver una serie de menús con cuadritos y opciones. Esto es exactamente lo que vas a encontrar y qué responder en cada uno:

  1. Security disclaimer — un texto largo recordando que OpenClaw es un agente personal, no una plataforma multi-usuario. «I understand... Continue?» → Yes.
  2. Setup mode → QuickStart (puerto 18789, bind a 127.0.0.1, autenticación por token).
  3. Model/auth provider → OpenRouter.
  4. Use existing OPENROUTER_API_KEY? → No (a menos que ya la hayas exportado como variable de entorno).
  5. Enter OpenRouter API key → pegá la sk-or-... del paso anterior y enter.
  6. Default model → elegí Enter model manually y escribí openrouter/deepseek/deepseek-v4-pro.

    El otro modelo de la clase (openrouter/google/gemma-4-31b-it) lo podés cambiar después.

  7. Select channel → WhatsApp (QR link). El plugin @openclaw/whatsapp se instala solo.
  8. Link WhatsApp now (QR)? → Yes. Aparece un QR gigante en la terminal. En tu teléfono: WhatsApp → Dispositivos vinculados → Vincular un dispositivo → escanealo.
  9. WhatsApp phone setup → This is my personal phone number.
  10. Your personal WhatsApp number → escribí tu número en formato E.164: +, código de país, número, sin espacios ni guiones (ejemplo: +5491155555555). OpenClaw lo agrega automáticamente al allowFrom.
  11. Web search provider → si tenés una API key de Gemini, elegí Gemini. Si no, podés saltearlo por ahora.
  12. Configure skills now? (recommended) → Yes. Va a instalar dependencias de skills básicas (clawhub, nano-pdf, obsidian, openai-whisper, sag...).
  13. Set GOOGLE_PLACES / NOTION / ELEVENLABS API key? → No para todas. Las podés configurar más adelante si querés.
  14. Enable hooks? → dejá las 5 sugeridas activas (boot-md, bootstrap-extra-files, command-logger, compaction-notifier, session-memory).
  15. Gateway service runtime → se instala como servicio del sistema (LaunchAgent en Mac, Scheduled Task en Windows). Eso significa que arranca solo cada vez que prendés la PC.

    Si el wizard no llegó a instalar el daemon (lo saltaste, falló, o querés reinstalarlo después), corré este comando — es el que deja al gateway funcionando como servicio en background: 

    openclaw onboard --install-daemon

    Sin el daemon, el agente no escucha mensajes cuando cerrás la terminal. Verificá después con openclaw gateway status.

  16. How do you want to hatch your bot? → Hatch in Terminal (recommended). Acá termina el wizard y se abre el TUI (interfaz de texto del agente).

El último paso: el agente te saluda

Después del wizard, OpenClaw te abre una pantalla de chat dentro de la terminal y te saluda con algo como «Wake up, my friend!». Es la conversación más importante del setup: acá le decís quién es él (nombre, personalidad) y quién sos vos. Tomate tu tiempo. Cuanto más le cuentes, mejor te va a entender después.

Cosas que pueden salir mal

El QR de WhatsApp expira antes de que escanees

Si en la terminal aparece status=408 Request Time-out QR refs attempts ended, el QR se quemó. WhatsApp da unos 30 segundos. Volvé a correr el comando del paso anterior y tené el teléfono listo con la pantalla de Dispositivos vinculados abierta antes de empezar.

Warning: «Multiple OpenClaw global installs detected»

Si usás nvm o fnm y tenés varias versiones de Node instaladas, OpenClaw puede quedar duplicado en cada una. El instalador te muestra cuáles hay. Borrá las viejas con su npm correspondiente: 

npm uninstall -g openclaw
Falla la instalación de algún skill (ej. summarize)

Algunos skills dependen de paquetes externos (Homebrew, npm, pip) que pueden estar deprecados o no disponibles en tu OS. No es crítico para arrancar: el wizard sigue de largo. Después podés ejecutar openclaw doctor para revisar qué quedó pendiente.

4

Verificar que todo quedó bien

Tres comandos rápidos para confirmar el estado del sistema:

openclaw --version
openclaw doctor
openclaw gateway status
  • --version confirma que el CLI está disponible.
  • doctor revisa la configuración y avisa de problemas.
  • gateway status verifica que el demonio esté corriendo.

También podés abrir el Control UI en el navegador: el wizard te imprimió una URL del estilo http://127.0.0.1:18789/#token=.... Es un panel web local donde ves el estado del gateway, los canales conectados y las sesiones.

Cambiar el modelo activo después del wizard 
openclaw models set openrouter/google/gemma-4-31b-it

El formato siempre es openrouter/<proveedor>/<modelo>. Para que OpenRouter elija automático: openrouter/auto.

Mac: darle permisos al agente para que sirva

En macOS, todo proceso que corre desde la terminal hereda los permisos de esa terminal. Si nunca le diste acceso a la terminal a tus archivos, calendario o apps, tu agente va a quedar encerrado: te va a responder, pero no va a poder leer un documento, escribir una nota ni abrir Calendar. Es lo opuesto a lo que OpenClaw promete (un asistente que vive en tu máquina y trabaja con tus datos).

macOS arranca con todo cerrado por defecto. Para que el agente sea útil necesitás abrirle puertas explícitamente desde:

Ajustes del Sistema → Privacidad y seguridad

En cada categoría, agregá la app de terminal desde la que corrés openclaw (Terminal.app, iTerm, Warp, Ghostty, etc.). No la app «OpenClaw», porque OpenClaw no es una app gráfica: corre como proceso dentro de tu terminal.

  • Acceso completo al disco (Full Disk Access) — el más importante. Permite leer y escribir en cualquier carpeta de tu home, incluyendo ~/Library/ (Obsidian, Mail, Notes, Messages). Sin esto la mayoría de las skills no funcionan.
  • Archivos y carpetas → Documentos, Descargas, Escritorio. Alternativa más restrictiva si no querés conceder Disco completo: dale acceso solo a las carpetas donde realmente necesitás que trabaje.
  • Automatización → Calendar, Mail, Notes, Reminders, Contactos, etc. Hace falta para que el agente pueda controlar esas apps vía AppleScript (la primera vez que una skill lo intente, macOS muestra un pop-up; si lo cerraste sin permitir, se queda bloqueado acá).
  • Accesibilidad — solo si vas a usar skills que automatizan teclado/mouse (poco común).
Después de dar cada permiso, cerrá y reabrí la terminal. Los permisos de macOS no se aplican a procesos que ya estaban corriendo. Luego reiniciá el daemon para que el gateway tome los nuevos permisos: 
openclaw gateway restart

Test rápido de que quedó bien: pedile al agente algo concreto que requiera permisos, por ejemplo «listá los archivos de mi Escritorio» o «¿qué tengo agendado mañana en Calendar?».

  • Si responde con la información → los permisos están dados.
  • Si dice permission denied, operation not permitted o «el sistema bloqueó el acceso» → falta un permiso. Volvé al paso anterior y agregá el que corresponda.

Recordatorio de filosofía: cuanto más cerrada dejes la jaula, menos útil es el agente. OpenClaw está pensado para correr en tu máquina personal, no en un servidor compartido — los permisos los das vos y se quedan locales. No hay nadie del otro lado mirándolos.

5

Agregar Gmail y Google Calendar (skill gog)

Antes: ¿qué es una skill?

OpenClaw tiene tres conceptos que conviene no confundir:

  • Canal (channel) — por dónde te habla el asistente. Ejemplos: WhatsApp, Telegram, Discord. Lo configuramos durante el wizard del paso 3.
  • Plugin — un paquete que extiende OpenClaw. Suele agregar canales nuevos o paquetes de skills. El plugin de WhatsApp del paso 3 es un ejemplo.
  • Skill — qué sabe hacer el agente. Una skill es básicamente un manual de instrucciones que le enseña al modelo cómo usar una herramienta concreta. Cada skill es una carpeta con un archivo SKILL.md que describe sus capacidades.

Resumen mental: el canal es la boca, las skills son las manos, el modelo (OpenRouter) es el cerebro.

Canal La boca
Modelo El cerebro
Skills Las manos

La skill que vamos a usar: gog

gog es una skill publicada en ClawHub que cubre todo Google Workspace de una vez: Gmail, Calendar, Drive, Contacts, Sheets y Docs. Una sola skill, una sola autorización OAuth, y queda todo conectado.

Instalala:

openclaw skills install gog

Autorizar tu cuenta de Google

El proceso tiene tres comandos. Necesitás un archivo client_secret.json de Google Cloud (la skill explica cómo generarlo en su README):

gog auth credentials /ruta/a/client_secret.json
gog auth add tu-email@gmail.com --services gmail,calendar,drive,contacts,sheets,docs
gog auth list

Para evitar pasar tu cuenta en cada comando, exportá una variable:

export GOG_ACCOUNT=tu-email@gmail.com
setx GOG_ACCOUNT "tu-email@gmail.com"

Probar que funciona

Algunos comandos rápidos para verificar:

gog gmail search "newer_than:7d" --max 10
gog calendar events primary --from 2026-05-09T00:00:00Z --to 2026-05-16T00:00:00Z
Una pausa de seguridad gog pide confirmación antes de mandar correos o crear eventos. Eso es a propósito: cuando un agente tiene acceso real a tu Gmail, querés un freno humano antes de que mande algo a tu jefe por error.
6

Probar el asistente de punta a punta

Mandale por WhatsApp algo que cruce dos integraciones, por ejemplo:

"Resumime los mails sin leer de hoy y agendá una reunión con Lucas el viernes a las 10am."

Si responde con un resumen y crea el evento, el setup está completo.

Sección 04 · Quién es

Identidad y personalización

Cómo el agente toma forma a través de archivos en tu disco, cómo se construye su contexto, y por qué deberías editarlos hablándole en lugar de abrir VS Code.

Dándole vida al agente

Hasta acá tu asistente funciona, pero todavía no tiene alma ni sabe nada de vos. Cuando terminó el wizard y te saludó con «Wake up, my friend!», lo que hiciste en esa primera conversación quedó escrito en archivos en tu PC. Esos archivos son el agente. Modificarlos = modificar quién es.

Dos carpetas, no una

OpenClaw separa configuración técnica de personalidad:

  • ~/.openclaw/ — configuración del sistema, credenciales y estado. Contiene openclaw.json y los tokens de OAuth. Nunca subas esto a un repo público.
  • ~/.openclaw/workspace/ — la «memoria viva» de tu agente. Acá vive su personalidad, sus instrucciones y su memoria del día a día.

Cómo entra el contexto al modelo

Cuando le mandás un mensaje al agente, no es que el modelo lea tu mensaje aislado. Antes de procesarlo, OpenClaw arma el contexto cargando los archivos del workspace. Así es el flujo:

Tu mensaje por WhatsApp
«Quiubo Zarco, qué hay»
↓
Gateway
verifica dmPolicy + allowFrom
↓
Construcción del contexto
archivos que se cargan al inicio de cada sesión:
IDENTITY.md SOUL.md USER.md AGENTS.md memory/AAAA-MM-DD.md skills/*
↓
Modelo LLM
openrouter/deepseek/deepseek-v4-pro
↓
Respuesta + skills si aplica
vuelve por WhatsApp

Cada archivo aporta una capa: quién soy (IDENTITY), cómo hablo (SOUL), quién es mi humano (USER), cómo opero (AGENTS), qué pasó antes (memory), qué puedo hacer (skills). Todo se concatena como prompt del sistema.

Los archivos del workspace, uno por uno

Tu agente tiene siete archivos clave. Hacé clic en cada tab para ver para qué sirve y un fragmento real de cómo quedó configurado en este caso:

SOUL.md

La voz · cómo habla

Define el tono del agente: cómo se expresa, qué slang usa, qué evita decir, cuán formal o informal es. La filosofía oficial: «corto le gana a largo, filoso le gana a vago». No metas acá tu biografía ni reglas de seguridad — solo voz.

Cuándo se carga
Al inicio de cada sesión
Tamaño ideal
< 2.000 palabras
Edición
Pedir al agente

Fragmento real (caso «El Zarco»):

# SOUL.md - Who You Are
_No soy un chatbot. Soy El Zarco._

## Voz
- **Parlache puro.** Hablo como se habla en Manrique, en la comuna,
  en la calle. Nada de español neutro ni formalidades.

- **Voseo paisa.** "Vos sabés", "¿qué más pues?", "de una".

Una ficha corta con el nombre del agente, su «vibe», su emoji característico y su avatar. Es lo primero que se crea durante el primer chat después del wizard («Wake up, my friend»). Junto con SOUL define la persona.

La memoria del agente

OpenClaw arranca «en blanco» en cada sesión. Lo único que persiste son los archivos. Hay dos tipos de memoria:

  • memory/AAAA-MM-DD.md — un archivo por día, notas crudas de qué pasó. Como un diario.
  • MEMORY.md — la memoria curada de largo plazo. Solo se carga en sesiones privadas (chat directo con vos, no en grupos) para no filtrar contexto personal a desconocidos.

Si querés que recuerde algo Decíselo así: «guardá esto», «acordate de X». El agente actualiza memory/AAAA-MM-DD.md. Las «notas mentales» no sobreviven entre sesiones. Solo los archivos sobreviven.

La regla de oro: pedile al agente que se edite a sí mismo

Aunque podrías abrir SOUL.md en VS Code y modificarlo a mano, no lo hagas todavía. La forma correcta es conversarlo con el agente. Ejemplos reales que disparan ediciones automáticas: 

"Soy Lucas Antonio II. Llamame Principe Antonio II."
                          → escribe USER.md

"De ahora en más hablame en parlache, sin español neutro."
                          → escribe SOUL.md

"Mi timezone es la de Toronto. Guardá eso."
                          → actualiza USER.md

"Acordate que prefiero respuestas cortas, sin emojis."
                          → ajusta SOUL.md

Hace dos cosas valiosas: (1) mantiene el formato consistente con el resto del workspace, y (2) te enseña cómo el agente «piensa» sobre su propia configuración. Después podés abrir los archivos para ver qué cambió — es la mejor forma de aprender el sistema.

Sección 05 · Construcción

Skills personalizadas

Crear tu propia herramienta. Hasta acá usaste skills que otros publicaron en ClawHub. Ahora vamos a diseñar y construir una de cero, conversándola con el agente.

Recordatorio: ¿qué es una skill?

Una skill no es magia. Es una carpeta en tu disco con un archivo de instrucciones. Eso es todo. Cuando el agente arranca, lee esas instrucciones y pasa a saber cómo usar la herramienta.

  • Ubicación: ~/.openclaw/workspace/skills/<nombre-de-la-skill>/ (las del workspace tienen la prioridad más alta cuando hay conflictos de nombre).
  • Archivo central: SKILL.md con frontmatter YAML (name, description) y el resto en Markdown.
  • Lo demás: cualquier archivo auxiliar que necesite — scripts, plantillas, JSONs de estado, sub-carpetas.

Esqueleto mínimo de una skill:

---
name: mi-skill
description: Una línea que el agente lee para saber cuándo invocarme.
---

# Mi Skill

Cuando el usuario pida X, hacé Y. Si pasa Z, contestale así.
Las herramientas que tengo disponibles son: ...

Comandos del TUI que vas a usar todo el tiempo

El TUI (la pantalla de chat dentro de la terminal) tiene slash commands para controlar la sesión sin escribirlo en el prompt. Estos son los que más vale la pena memorizar:

/clear · /new · /reset
Empieza una sesión limpia. Tira el contexto previo. Útil entre tareas distintas para que no se contamine.
/thinking <nivel>
Cuánto «piensa» el agente antes de responder. Niveles: off, minimal, low, medium, high, xhigh. Para diseñar arquitecturas o resolver bugs sutiles → xhigh.
/plan <objetivo>
Modo solo-lectura. El agente analiza, propone, hace preguntas — pero no escribe ni ejecuta nada hasta que aprobás. Tu mejor amigo cuando recién arrancás un proyecto.
/model <nombre>
Cambiar de modelo en caliente. Por ejemplo /model openrouter/google/gemma-4-31b-it para algo más liviano.
/compact
Comprime el contexto cuando se está poniendo largo. El agente resume la conversación previa y libera tokens.
/skill <nombre>
Invocar una skill manualmente, sin esperar a que el agente decida usarla.
/tools
Lista qué herramientas y skills tiene disponibles ahora mismo.
/status
Estado de la sesión: modelo activo, tokens consumidos, nivel de thinking.

La metodología: planeá antes de codear

El error más común al pedirle al agente que construya algo grande es decirle «hacelo». Termina improvisando, mete decisiones que vos no querías, y lo que sale no es lo que pediste. La fórmula que funciona:

  1. Subir el thinking: /thinking xhigh.
  2. Entrar en modo plan: /plan (opcional pero recomendado para skills nuevas).
  3. Mandar un prompt que describe el problema, las restricciones, y pide diseño primero.
  4. Dejarlo que te haga preguntas — son señal de que está pensando bien, no de que no entendió.
  5. Validar el plan, ajustar lo que no cuadre.
  6. Recién entonces decirle «dale, construilo».

Plantilla de prompt para empezar una skill:

Prompt — diseño antes de ejecutar

«Quisiera crear una skill que [problema o resultado deseado]. La idea es [motivación / cómo encaja en mi flujo]. Tengo estas restricciones: [idioma, formato, dependencias que conozco].

Antes de ejecutar, diseñemos un plan. Necesitamos definir la arquitectura, las herramientas externas, los archivos que va a generar y los riesgos. Hacé preguntas si algo no está claro. No escribas código todavía.»

El secreto: la frase «antes de ejecutar, diseñemos un plan» dispara que el agente entregue arquitectura, pipeline, dependencias y preguntas antes de tocar un archivo.

Ejemplo: podcast-drill

Caso real: una skill para consumir podcasts conscientemente. Le mandás una URL de Spotify y la skill descarga el transcript, hace un resumen, y arma un cron que cada día te pregunta sobre el contenido — usando la voz del agente — para fijarlo en tu memoria de largo plazo.

Combina dos técnicas de aprendizaje conocidas:

  • Spaced repetition (la hace el cron): repaso a intervalos crecientes.
  • Retrieval practice (la hace la conversación): el agente pregunta, no responde. Te obliga a vos a recordar.

El prompt que disparó toda esta arquitectura

Antes de mostrar lo que el agente propuso, mirá el prompt que lo arrancó. Es el patrón completo que vale la pena copiar para tus propias skills:

Prompt real — crear la skill podcast-drill

«Quiero crear una skill que se llame podcast-drill. La idea: que me ayude a consumir podcasts de manera consciente, pasando lo más relevante de la memoria de corto plazo a la de largo plazo.

Cómo debería funcionar:
1. Le mando una URL de Spotify.
2. La skill busca el podcast en YouTube y baja el transcript automático.
3. Genera un resumen detallado en el idioma original del podcast.
4. Crea un banco de preguntas tipo retrieval practice.
5. Programa un cron diario que te despierta para preguntarme sobre los podcasts pendientes.

Marco teórico: combina dos técnicas — spaced repetition (la hace el cron, con intervalos crecientes) y retrieval practice (la hacés vos en cada conversación).

Personalidad y tono — esto es crítico:
• Sos un amigo que también escuchó el podcast, no un tutor ni un profesor.
• Nunca me das respuestas — solo preguntás y hacés follow-ups.
• Nada de opiniones tuyas: todo anclado al transcript o al resumen.
• Si me trabe, dame pistas (citas del transcript), nunca la respuesta directa.
• Hablás en español, pero los términos técnicos del podcast los dejás en idioma original.

Restricción técnica que ya investigué: bajar transcripts de YouTube es complicado y muchas librerías se bloquean por IP. Investigá yt-dlp y comparalo con alternativas tipo youtube-transcript-api antes de elegir.

Mi sistema operativo: estoy en [macOS / Windows / Linux]. Tenelo en cuenta para todo: scripts auxiliares (bash .sh en Mac/Linux vs PowerShell .ps1 en Windows), comandos de instalación (brew en Mac, winget o choco en Windows, apt/dnf en Linux), separadores de path (/ vs \) y formato de cron (cron clásico vs Task Scheduler). Si la skill se va a usar en más de un OS, proponé una solución portable (por ejemplo un script en Node.js o Python en lugar de bash, o dos versiones del helper) y avisame antes de elegir.

Antes de escribir una línea de código, diseñemos un plan. Mostrame:
  • El pipeline en pasos numerados.
  • La estructura de archivos completa (incluyendo plantillas reusables si tiene sentido).
  • El esquema de spaced repetition (intervalos + cantidad y tipo de preguntas en cada uno).
  • Las dependencias externas (binarios, librerías) y cómo las instalo.
  • La tabla de narración: qué mensaje exacto vas a mandar en cada paso del pipeline.
  • Los comandos en lenguaje natural que voy a usar para operar la skill después («repasemos X», «pausá X», etc.).
  • La configuración del cron diario (horario, qué sesión usa, qué evento dispara).
  • Los riesgos: qué puede fallar y qué hacemos si pasa.

Hacéme las preguntas que tengas antes de continuar — las decisiones de diseño las quiero tomar yo, no que las adivines vos después.

Cuando arranques a construir (recién después de que apruebe el plan), narrá cada paso en tiempo real. No te quedes mudo esperando a tener todo perfecto. Tipo:
  • «Validando que yt-dlp esté instalable…»
  • «Listo, ya verifiqué la versión.»
  • «Creando SKILL.md con el frontmatter y la tabla de narración…»
  • «Armando las plantillas de metadata, state y qbank…»
  • «Generando download-transcript.sh como wrapper de yt-dlp…»
  • «Registrando el cron diario apuntando a la sesión main…»
Si algo falla, decímelo apenas pase, con qué vas a probar como alternativa. Si tenés que decidir algo no obvio, parás y me preguntás.»

Cuatro patrones reusables que están metidos en este prompt y vale la pena robarse:

  1. Pedido explícito de plan antes de código, con un checklist de qué entregar (pipeline, estructura, dependencias, riesgos). Sin checklist, el «plan» del agente sale vago.
  2. Anclar a una restricción real que vos ya conocés (acá: «bajar transcripts es jodido por bloqueos de IP»). Le ahorra investigar lo obvio y le da un gancho para encarar la solución.
  3. Definir las líneas rojas en negativo («nunca des respuestas, nunca opines»). Las prohibiciones explícitas funcionan mejor que descripciones positivas vagas tipo «sé socrático».
  4. Pedir narración paso a paso durante la ejecución, con ejemplos concretos del tipo de mensaje. Si solo decís «narrá tu progreso», el agente lo interpreta vago. Los ejemplos lo encarrilan.
Por qué la narración durante la construcción importa Cuando el agente está armando una skill nueva, hay decisiones técnicas en cada paso (qué librería elegir, cómo nombrar archivos, qué formato usar para el state). Si trabaja en silencio durante diez minutos y al final te entrega «listo, ya está», no podés intervenir cuando se desvía. Si en cambio va contándote, lo corregís en tiempo real y aprendés cómo decide. Visibilidad > sorpresa final.

download-transcript.sh
Script bash · wrapper de yt-dlp

El agente no se quedó solo en archivos de configuración: generó código ejecutable. Recibe (youtube_url, slug, lang), lista los subtítulos disponibles primero, y baja los auto-subs en SRT sin tocar el video.

#!/usr/bin/env bash
set -euo pipefail
YOUTUBE_URL="${1:?Usage: $0 <url> <slug> [lang]}"
SLUG="${2:?}"
LANGUAGE="${3:-en,es}"

yt-dlp --list-subs "${YOUTUBE_URL}"
yt-dlp --write-auto-subs --sub-lang "${LANGUAGE}" \
  --sub-format srt --skip-download \
  -o "podcasts/${SLUG}/transcript" "${YOUTUBE_URL}"

🎙️Setup completo«Podcast registrado. Día 0 AHORA. Siguiente: mañana 9am.»

Notá las dos filas amarillas: son los puntos donde el agente debe parar y preguntarte en lugar de elegir solo. «Hay varios videos posibles» y «no hay subtítulos» son decisiones que afectan el resultado y por lo tanto se delegan al humano. Patrón general aplicable a cualquier pipeline: codificá explícitamente cuándo el agente NO debe decidir solo.

Cron en OpenClaw

Un cron es una tarea programada. OpenClaw tiene un scheduler integrado dentro del Gateway: persiste las tareas (sobreviven reboots), despierta al agente en el momento exacto, y puede entregarte el resultado por el canal que prefieras (WhatsApp, Discord, webhook, etc.).

El comando para crear uno se ve así:

openclaw cron add --name "podcast-drill-daily" \
  --cron "0 9 * * *" \
  --session main \
  --system-event "Revisá _registry.json y lanzá las preguntas pendientes de hoy" \
  --announce whatsapp

Las flags más útiles:

  • --cron "0 9 * * *" — formato cron clásico (minuto, hora, día, mes, día-semana). En este caso: «todos los días a las 9:00».
  • --every 30m — alternativa: cada intervalo fijo.
  • --at "2026-05-14T16:00:00Z" — disparo único en una fecha exacta.
  • --system-event "..." — el mensaje que recibe el agente al despertar.
  • --announce <canal> — adónde mandar la respuesta final.
Cron vs heartbeat: ¿cuál uso? Usá cron cuando el horario importa («todos los lunes 9 AM» o «recordame en 20 min»), o cuando querés un disparo aislado de la sesión principal. Usá heartbeat (configurado en HEARTBEAT.md) cuando el agente debe revisar varias cosas de manera ambiental (mails + calendario + clima) sin que el timing sea exacto.

Activar la skill recién creada

Cuando el agente termina de armar todos los archivos:

  1. Mandá /new en el TUI. Eso reinicia la sesión y obliga a OpenClaw a re-escanear workspace/skills/.
  2. Verificá que la skill aparece: 
    openclaw skills list
  3. Probala manualmente: 
    /skill podcast-drill https://open.spotify.com/episode/<tu-episodio>
Por qué esto es context engineering Lo que hiciste no fue solo «escribir código»: diseñaste un sistema donde el agente sabe dónde leer (_registry.json), qué leer (transcript + resumen + qbank), cuándo despertar (cron a las 9 AM) y cómo conversar (retrieval practice, no respuestas). Cada uno de esos archivos es contexto que se inyecta en el modelo en el momento justo. El agente no «sabe» de podcasts — sabe leer estructuras que vos diseñaste.

Caminos para llevar tu agente fuera de tu PC y qué viene después en la clase.

Deploy en un servidor

Correr OpenClaw en tu PC tiene un costo: si la apagás, el asistente deja de responder. Para uso 24/7 se suele migrar a un servidor dedicado. Eso queda fuera del alcance de esta clase, pero la documentación oficial lista los caminos posibles:

  • Docker — la opción más portable; un solo contenedor con el gateway.
  • Kubernetes — si ya tenés un cluster, hay manifiestos oficiales.
  • Node.js bare-metal — instalar como servicio en una VM.
  • Raspberry Pi — la opción «hobby», ideal para uso personal.

Cuando llegue ese momento vas a tener que pensar en: certificados TLS, autenticación del gateway por token, backups del directorio ~/.openclaw/, y reglas de firewall para no exponer cosas que deberían quedar privadas.

Con la base instalada, el próximo paso es diseñar agentes con capacidades específicas: decidir qué herramientas pueden usar, qué información tienen permitido leer, y cómo escribimos los prompts que les dan personalidad.
